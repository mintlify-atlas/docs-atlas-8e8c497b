title: "Notifications"
description: "How Stockël generates, displays, and manages inventory notifications for released and delivered assignments."
---

Stockel tracks inventory events — specifically when a stock assignment is marked as released (liberado) or delivered (entregado) — and surfaces these events as notifications in the UI. Notifications are stored in the `NotificacionInventario` table and can be read, marked as read, or cleared by any authenticated user.

## NotificacionInventario model

The `NotificacionInventario` table stores every notification generated by the system:

| Field | Type | Description |
|---|---|---|
| `id` | `Int` | Auto-incremented primary key |
| `tipo` | `String` | Event type: `liberado` or `entregado` |
| `mensaje` | `String` (Text) | Human-readable notification message |
| `folio` | `String?` | Sales folio associated with the event (optional) |
| `clave` | `String?` | Product key (clave) involved in the event (optional) |
| `cantidad` | `Int` | Quantity of units affected. Defaults to `0` |
| `leida` | `Boolean` | Whether the notification has been marked as read. Defaults to `false` |
| `createdAt` | `DateTime` | Timestamp of when the notification was created |

The table has database indexes on `leida` and `createdAt` for efficient querying of unread notifications sorted by recency.

## When notifications are generated

Notifications are created by the inventory assignment processing logic whenever a sale's assignment status changes:

- **`liberado`** — generated when an active inventory assignment is cancelled. Stock that was reserved for a folio is released back to the warehouse.
- **`entregado`** — generated when an inventory assignment is marked as delivered. Stock has physically left the warehouse to fulfill the order.

The automated sales analysis cron job (`POST /api/cron/analisis-ventas`) runs every 10 minutes and processes incoming sales data from the SOAP service. When it detects a status change — a folio transitioning to `Cancelado` or `Entregado` — it calls `procesarAsignacionesPendientes`, which updates the corresponding `AsignacionInventario` records and creates `NotificacionInventario` rows for the affected products and folios.

<Info>
The cron endpoint authenticates using a `CRON_SECRET` Bearer token set in the server environment. It does not use the standard user JWT. Only the VPS cron job should call this endpoint.
</Info>

## Notification API

Three endpoints manage notifications. All require a valid user session.

### Fetch notifications

```http
GET /api/notificaciones
```

Returns the 50 most recent notifications ordered by `createdAt` descending, along with a count of unread notifications:

```json
{
  "success": true,
  "notificaciones": [
    {
      "id": 42,
      "tipo": "entregado",
      "mensaje": "Asignación entregada: folio QRO12155, clave CGK, 2 unidades",
      "folio": "QRO12155",
      "clave": "CGK",
      "cantidad": 2,
      "leida": false,
      "createdAt": "2026-03-17T14:30:00.000Z"
    }
  ],
  "noLeidas": 3
}
```

### Mark all notifications as read

```http
PUT /api/notificaciones
```

Sets `leida = true` on every notification where `leida = false`. Returns `{ "success": true }`. Use this when the user opens the notification center.

### Clear all notifications

```http
DELETE /api/notificaciones
```

Permanently deletes all notification records. This action cannot be undone.

<Warning>
The DELETE endpoint removes all notifications for all users — there is no per-user scoping. Only use it to perform a full notification reset.
</Warning>

## Notification center in the UI

The notification center is accessible from the main application layout. It shows:

- A badge with the count of unread notifications (`noLeidas`) when there are any
- A list of the 50 most recent notifications, newest first
- Each entry displays the `tipo`, `mensaje`, `folio`, `clave`, `cantidad`, and `createdAt` timestamp
- Unread notifications are visually distinguished from read ones

Opening the notification panel triggers a `PUT /api/notificaciones` call to mark all visible notifications as read. The unread badge clears automatically.

<Tip>
The notification center polls or refreshes on navigation. If you expect high-frequency inventory events, consider opening the panel periodically to keep the unread count accurate.
</Tip>

## Automated processing via cron

The sales analysis cron job is the primary source of notifications. Here is how it connects to the notification system:

<Steps>
  <Step title="Cron fires every 10 minutes">
    The VPS scheduler sends `POST /api/cron/analisis-ventas` with the `Authorization: Bearer <CRON_SECRET>` header. The endpoint is authenticated and has a maximum execution time of 5 minutes.
  </Step>
  <Step title="SOAP data is fetched and processed">
    The cron downloads current-day sales from the SOAP service, including cancellations and deliveries, and reconciles them against the `Venta` table in the database.
  </Step>
  <Step title="Assignment statuses are updated">
    For each folio that changed to `Cancelado` or `Entregado`, `procesarAsignacionesPendientes` is called. It updates the relevant `AsignacionInventario` rows and writes a new `NotificacionInventario` record with the appropriate `tipo`, `folio`, `clave`, and `cantidad`.
  </Step>
  <Step title="Notification appears in the UI">
    The next time any authenticated user fetches `GET /api/notificaciones`, the new record appears in the list with `leida = false`.
  </Step>
</Steps>

## Notification types reference

| Type (`tipo`) | Trigger | Meaning |
|---|---|---|
| `liberado` | Assignment cancelled (folio status → `CANCELADO`) | Reserved stock has been released back to inventory |
| `entregado` | Assignment delivered (folio status → `ENTREGADO`) | Stock has been physically delivered to the customer |
